This little box is now the phone book your home network uses. Every time a TV, phone or laptop looks up an address, it asks this Pi. When the address belongs to an ad or a tracker, the Pi simply says “that doesn’t exist” — so the ad never loads, on every device, with nothing to install on any of them.

Tell your router to use this Pi as its DNS server.

Type this address into your router …

Log in to your router (usually 192.168.1.1 in a browser), find DHCP or LAN settings, and set the DNS server to the address above. Save, then restart one device to test.

Show me where it is on my router
  • BT Smart Hub / EE: Advanced settings → Home network → LAN IP → “Primary DNS”.
  • Virgin Media Hub: Advanced settings → DHCP → “Primary DNS server”.
  • Netgear / Nighthawk: Internet → “Use these DNS servers” → Primary DNS.
  • TP-Link: Network → DHCP Server → “Primary DNS”.
  • ASUS: LAN → DHCP Server → “DNS Server 1”, and set “Advertise router's IP…” to No.
  • Linksys: Connectivity → Local Network → DHCP Server → Static DNS 1.
  • Google Nest Wifi: Wi-Fi app → Settings → Advanced networking → DNS → Custom.
  • Eero (needs Eero Plus): Settings → Network settings → DNS → Custom.
  • Xfinity / Sky / locked routers: you often cannot change DNS. Use the Pi's own DHCP server instead: turn your router's DHCP off, then open the DHCP tab here.

Only one DNS server should be listed. If your router insists on two, put this address in both boxes — otherwise devices will quietly use the other one and see ads.

Let's check it is really working.

A device only starts using the new DNS after its lease renews. Turning its Wi-Fi off and on again (or rebooting it) is the quickest way.

Finally, protect this dashboard with a password.

Anyone on your Wi-Fi can open this page. A password stops a guest (or a curious teenager) from switching the filter off. You can skip it and add one later in Settings.

Write it down somewhere. If you lose it, run sudo adblockerpro -set-password on the Pi to set a new one.

Plain English help

The five-minute version

  1. Your router tells every device “ask this Pi for addresses”.
  2. The Pi checks the address against lists of known ad and tracker servers.
  3. Ads get a dead end. Everything else gets a real answer, cached so it's fast.

Something stopped working

  1. Open Query log and type the device or app name in the filter.
  2. Find a red blocked line that looks related.
  3. Press allow next to it. Try the app again.
  4. Still broken? Press Pause 5 min at the top. If it works while paused, it was us; if not, it wasn't.

Words you'll see

DNS
The internet's phone book: turns netflix.com into a number computers can call.
Query
One look-up in that phone book. A single web page can cause dozens.
Sinkhole
The dead-end answer we give for ads. “0.0.0.0” means “nowhere”.
Upstream
The public resolver we ask about everything that isn't blocked (Cloudflare, Quad9…).
Cache
Answers we remember for a while, so repeat look-ups are instant.
DHCP
How devices get their network settings. Whoever runs DHCP decides which DNS they use.
DoH
DNS-over-HTTPS: look-ups encrypted so your broadband provider can't read them.
TTL
How long an answer stays fresh before we ask again.
Block rate
Share of look-ups we refused. 10–40% is normal; 0% means devices aren't using the Pi yet.

Security

Point your network here

  1. Give the Pi a static IP (or a DHCP reservation) on your router.
  2. In the router's DHCP settings, set the DNS server to that IP.
  3. Reboot the streaming devices (or wait for their DHCP lease to renew).
  4. Block outbound port 53 to everything except the Pi so devices with hard-coded resolvers cannot escape.
